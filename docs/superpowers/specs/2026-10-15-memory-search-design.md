# “记忆寻迹”设计规格

- 日期：2026-10-15
- 状态：已确认，待编写实施计划
- 产品：照片记忆本
- 设计类型：现有“时间线”与首页搜索的统一升级

## 1. 背景与决策

当前产品已经具备两项基础回看能力：

1. 首页提供本地关键词搜索，可匹配已加载记忆的标题、备忘录、心情、状态和主题。
2. 底部导航提供“时间线”，按日期浏览全部已加载记忆。

如果另建一个独立的“记忆寻迹”模块，会同时产生两套搜索入口、两个相似时间流页面和两套记忆查询逻辑。用户难以判断应该使用“搜索”“时间线”还是“记忆寻迹”，技术上也会重复维护筛选、软删除、分页和记忆视图转换。

因此采用以下合并方案：

- 将底部导航中的“时间线”升级并更名为“记忆寻迹”。
- 首页现有搜索框改为“记忆寻迹”的快捷入口，不再在首页执行另一套本地过滤。
- 未设置搜索条件时，“记忆寻迹”继续承担原时间线的全部记忆浏览能力。
- 设置条件后，同一个页面展示符合条件的叙事时间流。
- 后端扩展现有 `MemoriesModule`，不新建重复的搜索业务模块。

## 2. 产品目标

让用户在不上传自然语言原句、不分析照片画面、不依赖云端 AI 推断的前提下，准确找到某段真实经历，并回到对应的原始照片与文字。

成功标准：

- 用户可以通过条件筛选、关键词或本地自然语言查找原始记忆。
- 系统展示的每一项结果都是现有原始记忆，不生成经历、情绪分析或回答。
- 搜索结果可追溯到记忆详情，并继续进入现有编辑流程。
- 新功能替代现有首页本地搜索和时间线，不新增含义相近的并列模块。

## 3. 功能边界

### 3.1 搜索范围

首版只检索原始记忆及以下字段：

- 发生时间
- 标题
- 备忘录
- 当日心情
- 当日状态
- 当日主题

结果可以标注该记忆所属的长期副本，但长期副本、记忆回声、月度总结和年度总结本身不进入搜索索引。

### 3.2 与现有模块的分工

- **记忆寻迹**：用户主动浏览全部记忆或按条件寻找真实记录。
- **长期副本**：用户围绕一个主题持续自动收集记忆，并管理进行中、暂停、完成和归档状态。
- **记忆回声**：系统主动唤起旧记忆，用户不需要先输入搜索条件。
- **情绪电影**：按月或按年整理已有记录，形成总结型回看体验。
- **重要日子**：用户主动维护纪念节点，而不是执行临时检索。

主题筛选可能与某条长期副本包含相似记忆，但两者目的不同，均保留。搜索结果仅标注关联副本，不自动重定向，也不替代长期副本。

### 3.3 首版不做

- 照片画面识别、OCR、人物识别和地点识别。
- 云端 AI、向量搜索、经历推理或自动生成回答。
- 近义词扩展和情绪含义推测。
- 搜索长期副本、记忆回声、月度总结或年度总结内容。
- 搜索收藏、随机回看、语音搜索和跨设备同步搜索历史。
- 将搜索行为写入总结、推荐或用户画像。
- 修改现有记忆字段和现有总结生成规则。

## 4. 信息架构与入口

### 4.1 首页入口

首页保留现有搜索框的视觉位置，但取消 `searchMemories` 本地过滤行为：

- 点击搜索框即进入“记忆寻迹”。
- 首页入口采用明确的按钮形态；点击后进入独立寻迹页，再输入描述并在本地解析。
- 首页仍展示照片墙、记忆回声和情绪电影卡片，不在首页渲染另一套搜索结果。

### 4.2 底部导航

原“时间线”入口更名为“记忆寻迹”，继续使用原导航位置，不增加第五个底部导航项。

### 4.3 页面状态

“记忆寻迹”页面具有以下状态：

1. **全部记忆**：没有搜索条件时，展示全部原始记忆的叙事时间流。
2. **条件编辑**：显示自然语言输入、关键词输入和结构化筛选面板。
3. **条件确认**：展示识别出的时间、心情、状态、主题和待确认关键词；用户确认后才搜索。
4. **结果列表**：展示已生效条件、结果总数和按月份分组的时间流。
5. **无结果**：明确说明没有匹配结果，并提供可移除条件建议。
6. **加载失败**：保留已显示结果和滚动位置，允许重试。

## 5. 查询方式

### 5.1 结构化筛选

用户可直接选择：

- 起止时间
- 一个心情
- 多个状态
- 多个主题
- 一个或多个关键词
- 排序方式

### 5.2 本地自然语言解析

自然语言只在浏览器中解析，不把原句发送到后端。解析器只识别：

- 现有主题名称
- 现有心情名称
- 现有状态名称
- 明确日期和日期范围
- 今天、昨天、本周、上周、本月、上个月、今年、去年、最近若干天

所有时间范围按 `Asia/Shanghai` 计算，一周从周一开始。首版不识别季节、“那段时间”“以前”“很久之前”等模糊时间。

解析完成后：

- 已识别内容转换为可编辑的条件标签。
- 无法识别的剩余文字标记为“待确认关键词”。
- 用户可以保留、修改或删除待确认关键词。
- 用户点击“开始寻迹”后才向后端发送结构化条件。

### 5.3 匹配关系

全部已确认条件之间使用“并且”关系：

- 心情只能单选，记忆心情必须相同。
- 选择多个状态时，记忆必须包含全部已选状态。
- 选择多个主题时，记忆必须包含全部已选主题。
- 多个关键词必须全部出现；每个关键词可以分别出现在标题或备忘录中。
- 关键词不搜索照片文件名、照片内容、心情、状态或主题；这些内容使用各自的结构化条件检索。

## 6. 精确搜索、模糊搜索与排序

### 6.1 默认精确搜索

- 文字匹配不区分大小写。
- 有关键词时默认按匹配程度排序。
- 没有关键词时默认按记忆发生时间从新到旧排序。
- 用户可以切换“最新优先”或“最早优先”。

匹配程度至少保证标题命中的权重高于备忘录命中；分数相同时按发生时间和记忆 ID 稳定排序。

### 6.2 错别字模糊搜索

精确搜索没有结果时：

1. 系统先显示无结果，不自动展示相似记忆。
2. 系统询问用户是否尝试错别字模糊搜索。
3. 只有用户确认后才启用 PostgreSQL `pg_trgm` 相似度匹配。
4. 模糊搜索仍要求时间、心情、状态和主题条件全部满足。
5. 首版不进行近义词扩展。

### 6.3 无结果建议

后端可以计算“移除单个条件后是否存在结果”，最多返回三条放宽建议。建议只说明可以移除哪个条件，不自动重新搜索；用户确认后再发起新查询。

## 7. 结果展示与交互

### 7.1 叙事时间流

结果使用已确认的 A 方案：

- 按月份分组。
- 每条直接展示照片、发生时间、标题、备忘录摘要、心情、状态和主题。
- 存在关联长期副本时显示副本名称，但不将同一记忆重复展示。
- 页面顶部显示结果总数和已生效条件。

未设置条件时同样使用该时间流展示全部记忆，从而完整替代原时间线页面。

### 7.2 增量加载

- 首次加载 5 条。
- 用户向下滚动时每次继续加载 5 条。
- 页面提供“回到顶部”。
- 分页使用稳定游标，避免新增或修改记忆后产生重复记录。

### 7.3 详情与编辑

- 点击结果进入现有记忆详情的只读状态。
- 用户点击“编辑”后才进入现有编辑流程。
- 返回寻迹页时恢复条件、已加载结果和滚动位置。
- 编辑完成后重新校验该记忆；不再符合条件时从结果中移除，并说明原因。
- 记忆被删除时从结果中移除，不导致整页报错。

## 8. 最近搜索

- 当前设备最多保存最近 20 条搜索。
- 保存自然语言显示文本和已确认的结构化条件，方便再次执行。
- 相同结构化条件自动去重，并更新到最前方。
- 支持单条删除和全部清空。
- 搜索历史只保存在当前浏览器，不创建数据库表。
- 搜索历史不进入 JSON、ZIP、PDF或数据库备份恢复范围，也不参与总结生成。
- 清除浏览器数据、切换设备或重新安装后，历史可以丢失。

首版不提供收藏、重命名或置顶搜索。

## 9. 前端设计

前端应复用现有导航、记忆卡片、详情和编辑能力，并把寻迹功能拆分为职责清晰的单元：

- `MemorySearchPage`：协调页面状态、条件、结果和滚动恢复。
- `MemorySearchInput`：接收自然语言或普通关键词。
- `MemorySearchFilters`：编辑时间、心情、状态、主题和排序。
- `MemorySearchConfirmation`：展示并确认本地解析结果。
- `MemorySearchTimeline`：按月份呈现结果并触发增量加载。
- `memory-query-parser`：纯本地、可单元测试的日期与标签解析器。
- `memory-search-history`：管理浏览器内最近 20 条历史。

首页不再调用现有 `searchMemories` 生成结果；原 `Timeline` 内联组件由寻迹页面替代。现有 `MemoryDetail` 和 `MemoryForm` 继续复用。

如果后端不可用，寻迹页不得把局部本地草稿冒充为完整数据库结果。页面应明确显示“完整搜索暂不可用”，保留当前已加载内容，但不承诺结果完整。

## 10. 后端设计

### 10.1 模块边界

搜索属于原始记忆读取能力，因此扩展现有 `MemoriesModule`，不创建平行的 `MemorySearchModule`。

现有 `GET /api/memories` 保留，继续服务当前列表读取和兼容调用。高级寻迹新增：

`POST /api/memories/search`

使用 POST 是为了避免关键词和结构化条件出现在 URL、浏览器历史或常规访问日志中。自然语言原句仍不会发送到该接口。

### 10.2 请求结构

```ts
type MemorySearchRequest = {
  from?: string;
  to?: string;
  mood?: string;
  statusValues?: string[];
  topicIds?: string[];
  keywords?: string[];
  matchMode?: 'EXACT' | 'FUZZY';
  sort?: 'RELEVANCE' | 'NEWEST' | 'OLDEST';
  cursor?: string;
  pageSize: 5;
};
```

限制：

- 自然语言或关键词总长度最多 100 个字符。
- 最多 5 个关键词。
- 最多 10 个状态。
- 最多 10 个主题。
- 页面大小固定为 5，后端仍进行上限校验。

### 10.3 响应结构

```ts
type MemorySearchResponse = {
  items: MemoryView[];
  total: number;
  nextCursor?: string;
  relaxationSuggestions?: Array<{
    field: 'from' | 'to' | 'mood' | 'status' | 'topic' | 'keyword';
    value: string;
    resultCount: number;
  }>;
};
```

### 10.4 数据库与安全

- 继续使用现有用户范围和 `deletedAt: null` 软删除条件。
- 普通结构化条件优先由 Prisma 组合查询。
- 多状态、多主题“全部包含”使用关系数量或等价的参数化查询实现。
- 匹配度排序和 `pg_trgm` 模糊匹配可使用 Prisma 参数化原生 SQL，禁止拼接用户输入。
- 为事件时间、状态数组和主题关联补充适用索引；标题和备忘录按实际查询计划增加 trigram 索引。
- 服务日志不记录关键词、标题、备忘录或完整请求体。

## 11. 异常处理

- 没有条件时视为“浏览全部记忆”，这是合并原时间线后的正常状态。
- 某条搜索历史引用已删除的主题或状态时，标记失效条件，要求用户删除或重新选择。
- 加载下一批失败时保留当前结果、条件和滚动位置，提供重试。
- 图片文件缺失时继续展示文字内容，并显示缺图占位符。
- 游标失效时重新执行当前查询并恢复到最接近的位置，不混入不同条件的结果。
- 模糊搜索仍无结果时停止自动放宽，只提供人工修改建议。
- 应用锁开启且未解锁时，不能进入寻迹页或查看最近搜索。

## 12. 测试与验收

### 12.1 前端测试

- 本地解析器覆盖所有支持的日期和相对时间，包含跨月、跨年和周一边界。
- 已知主题、心情和状态正确提取；未知文字进入待确认关键词。
- 首页按钮能够进入寻迹页，首页不再产生独立过滤结果，也不伪装成可输入但会立即跳转的文本框。
- 无条件时展示全部记忆；有条件时显示确认步骤和结果。
- 条件、滚动位置和已加载结果在详情返回后恢复。
- 最近搜索去重、20 条截断、单条删除和全部清空正确。
- 应用锁未解锁时不渲染寻迹内容。

### 12.2 后端测试

- 时间、心情、状态、主题和关键词严格执行“全部满足”。
- 多个状态与多个主题验证包含全部选择，而不是任意命中。
- 关键词只查询标题和备忘录。
- 精确、模糊和三种排序稳定且可分页。
- 5 条增量加载无重复、无遗漏。
- 软删除和用户范围始终生效。
- 无结果建议不会自动返回放宽后的记忆。
- 原生 SQL 全部参数化，超长或超量条件被拒绝。

### 12.3 回归测试

- 照片上传、批量导入、记忆编辑和删除不受影响。
- 长期副本自动收集、时间线和生命周期不受影响。
- 记忆回声、情绪电影、重要日子和数据保险箱不受影响。
- 现有 `GET /api/memories` 调用保持兼容。

### 12.4 性能目标

以 10,000 条记忆元数据为基准，在本机正常 PostgreSQL 环境中，首批 5 条结果目标在 1 秒内返回，不包含原始大图解码时间。应使用 `EXPLAIN ANALYZE` 检查精确搜索、组合筛选和模糊搜索的查询计划。
